# 提醒同步与回复展示修复

2026-09-27。本轮继续真实设备验证中发现的问题；不改产品版本，不部署云端。

## 已复现的漏提醒问题

Android 使用普通非精确闹钟，设定时间到了不代表通知已经展示。此前实测的一条提醒晚61.324秒投递，说明系统存在合法的待投递窗口。

原客户端每次同步先取消所有通知，再仅安排未来的规则。模拟器中创建了12:00的合成提醒，在时间到后仍确认系统有1条待投递闹钟；下拉刷新后变成0条，之后也没有显示通知。证据为 `output/verification/device-qa/pending-refresh-cancelled.json`。因此这是实测复现的问题，不只是推测系统可能延迟。

## 同步规则

改用通知插件已有的 pending/active/cancel API 逐条同步：

- 精确核对账号、事项、规则及版本、UTC触发时刻、标题和用途；将这份身份信息写入通知 payload，同时保留原来的点击路由字段。
- 对已经由系统接收且内容未变的提醒，保留其待投递状态，即使名义触发时间已经过去。
- 对没有在系统队列中的过期提醒，不创建新的通知，因此没有“补发历史提醒”。
- 删除、关闭、变更版本或触发时间、账号变化会移除原提醒。实际切换账号及退出仍清空通知。
- 保留的逾期待投递提醒计入450条上限，再按时间选择近期未来提醒；分配新ID时保留已有ID并避开冲突。
- 冷启动保留当前账号的待投递提醒，清理其他账号待投递通知及不在待投递快照中的已展示通知。初始化清理与同账号刷新使用独立的任务代次，避免刷新中断清理。
- 队列失败仍通知调用方，但不会再产生未处理的第二个异常；后续重试继续执行。

旧版 payload 只有账号和事项，无法证明旧提醒的完整版本与触发时刻。升级时取消不可核验的旧条目，仅重建未来规则，不重建过期条目。不能声称能保住升级前已经逾期、且不带完整身份信息的旧提醒。

实现覆盖：`reminder_sync.dart`、`android_notifications.dart`、`items_controller.dart`。定向测试先复现错误再验证修复，最终34项通过，覆盖等待期间退出、换账号、同账号刷新、跨触发时刻、ID冲突和条数上限；代码经独立规格及质量审阅。完整回归与构建证据另保存在 `output/notification-final-*`。

## 回复展示

实测追问时，模型返回的 Markdown 星号会直接显示。使用 [flutter_markdown_plus 1.0.12](https://pub.dev/packages/flutter_markdown_plus) 呈现列表、强调和可选择文字。该组件采用BSD-3-Clause许可，版本及校验锁在pubspec.lock。

模型回复不会自动加载外部图片，也不会执行链接。真实导航与确认操作继续走应用提供的结果卡。字体放大和既有助手交互共12项定向检查通过，渲染证据为 `output/verification/feedback-ui/assistant-rich-answer.png`。

用户已明确选择稍后再测有效语音；此项保持暂缓。实体手机兼容性与性能仍未验证。自动安装受工具策略限制，用户已授权，无需再次索要权限，但安装动作仍需用户手工执行。
