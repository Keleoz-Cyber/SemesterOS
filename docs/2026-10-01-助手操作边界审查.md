# 助手操作边界审查与验证

## 本轮范围

从“国庆节一号到7号都没课”被拒绝的实际截图出发，检查模型提示词、工具描述、服务端校验、课表投影、重新导入、学期设置、提醒、撤销及前端确认交互。当前用户管理的是自己的日程副本，课表导入来源不决定个人记录是否可修改，任何改动都不会写入学校教务系统。

## 已修正的限制

| 场景 | 原问题 | 现在的处理 |
| --- | --- | --- |
| 明确陈述放假或停课 | 与导入记录冲突时索要学校通知或反复询问 | 先查询受影响课次，直接生成停课预览，保存一次确认 |
| 同一门课多次出现 | 范围操作被当成必须逐条选择的歧义 | 已查询的完整范围可作为操作对象；真正不明确的单次操作再问日期 |
| 补录、更正过去课次 | 开始时刻已过就拒绝 | 允许更正和撤销；仍检查后续修改与依赖，保留历史 |
| 用户说改到某时刻，原时长未变 | 要求重新提供结束时刻 | 使用已记录的课程时长计算结束，并在预览展示 |
| 只有日期、周次或没有期限 | 因缺少时刻要求补齐 | 按已有精度记录，不制造时刻、地点或耗时 |
| 用户明确当天结束为截止 | 助手即使得到明确指令也拒绝日末截止 | 允许明确的日末截止；只有日期仍不自动解释为日末 |
| 已确定考试只作参考 | 正式状态强制预留时间 | 确定性与是否预留独立，日历、容量、统计采用同一选择 |
| 考试时间未定，用户指定提醒日期 | 提醒被强行绑定考试日期 | 指定时刻提醒独立执行；相对提醒仍依赖实际锚点 |
| 同名会议已补充日期或地点 | 仍强制点选 | 日期/地点查询唯一时直接定位，无法区分时才点选或再问 |
| 完成任务、取消考试或恢复事项 | App 手动支持，助手工具未接通 | 已接通状态变更工具，预览显示提醒及关联未来计划影响 |
| 考试已经考完 | 以“不是个人任务”为由禁止标记完成 | 可记录已完成，不改变考试类型、不猜成绩或实际耗时 |
| 未变更的预览过一天才保存 | 按统一24小时有效期拒绝 | 以真实数据版本、依赖和时间窗口校验，不因任意年龄拒绝普通记录 |
| 设置任务最早开始 | 助手无法设置，排程容易卡在未配置状态 | 可通过任务修改工具设置现在起或指定时刻 |
| 有调课后编辑、删除或导入课程 | 存在修改历史就锁死 | 基础数据可继续更正，明确的课次例外重放；删除不复活历史调课 |
| 有个人计划或停课后调整节次校历 | 要求先取消所有计划或核对历史却无可继续入口 | 保存设置后重算普通课程，保留明确调课，提示受影响计划而不自动移动 |
| 学期中已有其他冲突 | 无关修改也要求重复确认全部冲突 | 只对本次新增或扩大冲突要求确认 |
| 全学期课程查询 | 强制用户拆成32天范围 | 课次查询支持30周，普通日程查询支持一年；大量结果使用服务端缓存和分页 |
| 回复冗余 | 回复再次完整枚举结果卡片，附加无关引导 | 查询默认只给简短结论；详情由卡片承载 |

课程仍是个人任务自动排程的固定约束。用户只要求找空闲或安排学习时，求解器不会因此取消或移动课程。肯定的停课陈述与“是否停课”的问题分开处理。

## 保留的必要校验

账号和学期归属、真实对象与版本、过期预览不得覆盖新数据、幂等保存、一次可见保存确认、来源文本不自动产生操作、字段值的有效性、相对提醒的实际时间依赖、已有锁定计划的显式处理，以及后续依赖已经改变时不能整批强行撤销。未填写的信息可以保存，仅操作确实依赖它时才询问。

技术数量上限不作为权限解释：批量事务当前最多8个分组操作，范围停课的整个范围属于一个操作，可包含最多1000课次；记录卡片缓存200项并可分页。超过服务规模的请求需要拆分，不是要求学校授权。

## 独立代码审查

按 requesting-code-review 流程独立检查，发现并修正三个可复现回归：更正基础课程星期会丢失已确认调课；撤销后的普通课次固定在旧校历日期；连续周课次在校历平移后发生 ID 复用，可能取消错误课次。均先增加会失败的 API 用例，再修正重放。变更课次现在保留稳定的原课次身份，普通课次恢复使用最新基础投影。最终限定复查确认第三个场景通过。
