# 拾日开发说明

拾日把课程、个人日程、待办和学习计划放在同一个学期里管理。Flutter 客户端负责展示和操作，Python 服务端负责保存、冲突检查和排程。助手调用这些已有功能，不另建一套日程，也不能凭一句回复直接改数据。

这份说明供接手开发的人阅读。字段和接口的完整定义仍以代码为准。

## 1. 先认识项目里的几种记录

| 记录 | 用来表达什么 | 主要代码 |
| --- | --- | --- |
| 学期 | 学期名称、第一周的周一、总周数、每天的节次时间 | [academics.py](../services/api/app/academics.py) |
| 课程 | 哪些周、星期几、哪些节次上课。展开后得到某一天的具体课次 | [occurrences.py](../services/api/app/occurrences.py) |
| 日程 | 会议、彩排、比赛等活动，允许只知道日期或开始时刻 | [calendar_events.py](../services/api/app/calendar_events.py) |
| 事项 | 作业、一般待办和考试。待办可有剩余耗时，考试使用自己的考试时间 | [items.py](../services/api/app/items.py) |
| 学习时间 | 每周愿意学习的时段，以及临时不可用的时间 | [planning.py](../services/api/app/planning.py) |
| 学习计划 | 为某项任务安排的一段具体学习时间，可固定或取消 | [schedule_api.py](../services/api/app/schedule_api.py) |
| 助手对话 | 用户消息、处理过程、待确认的修改和保存结果 | [agent_api.py](../services/api/app/agent_api.py) |

“任务还要做 60 分钟”和“今晚安排了 60 分钟”是两件事。排进日历并不等于完成任务，所以保存计划不会自动减少剩余耗时。实际进度由用户另外记录。

课程也分“整门课”和“具体一次课”。调课、停课、请假针对课次记录处理，不应通过删除整门课来代替。

数据库表在 [models.py](../services/api/app/models.py)，请求字段在各模块对应的 `*_schemas.py`。数据库连接在 [database.py](../services/api/app/database.py)；迁移文件位于 `services/api/alembic/`。

## 2. 时间怎么保存，怎么使用

系统按上海时区解释日期和学期周次。具体时刻必须带时区，进入服务端后转换为 UTC；只有日期的信息仍保存为日期，不补成午夜。

时间记录分两层：一层说明知道多精确，另一层说明这个时间是做什么用的。

| 用户说法 | 保存方式 | 后续处理 |
| --- | --- | --- |
| 明天 9 点开会，几点结束不知道 | 具体开始时刻，结束为空 | 可以保存；检查 9 点是否撞课，不假定全天开会 |
| 周五交材料 | 日期 | 可以保存；不擅自推成周五 23:59 截止 |
| 第 12 周考试 | 周次 | 可以保存；不把整周都算成考试占用 |
| 10 日到 12 日办理 | 日期范围，标为办理窗口 | 这是可办理范围，不是连续三天都不能安排别的事 |
| 周六全天外出 | 日期，标为全天 | 按明确说出的全天占用处理 |
| 有空记得整理资料 | 时间未知 | 保存待办，不强迫选日期 |

“预计周五”和“周五”还涉及消息是否确定，不能只凭有没有钟点判断。记录用 `certainty` 表示确定程度，用 `time.precision` 表示时间精度，用 `time.meaning` 区分截止、开始、办理窗口、候选日期和全天等用途。

待办可以不填耗时、开始时间或截止。只有用户要自动安排学习时间时，系统才需要相应的信息：

- 剩余耗时不明，无法知道该排多少分钟，需要先补充。
- 普通任务没有说明等待条件，可以在本次规划范围内开始，不必逐项追问“几点能开始”。原记录不因此被改成一个虚构的开始时刻。
- 明确说“等审批结果出来再做”，必须保留这个条件，不能按立即可做来安排。
- 没有截止时间的任务也能排程，使用用户选择的规划范围；不能为了排程捏造一个截止时间。

时间字段检查见 [item_schemas.py](../services/api/app/item_schemas.py)，开始条件判断见 [task_readiness.py](../services/api/app/task_readiness.py)。

## 3. 保存前如何处理冲突

手工表单与助手保存日程共用冲突检查。新增或改时间时，先比较修改前后，找出这次新产生的冲突和受影响的学习计划。

例如课程是 8:00—9:50，用户新增 9:15 开始的会议。即使会议没有结束时间，也能确定 9:15 需要同时上课和开会，因此要在保存前让用户处理。可补充或调整时间，确认已经为具体课次请假，或明确选择保留重叠安排。

如果会议只说 7:30 开始、没有结束时间，系统不能据此断言 8 点的课必然冲突。它保留“结束时间未说明”的提示，而不是要求请掉当天所有课。原文明确要求提前到场时，已知的提前到场时间也参与检查。

请假只记录用户选中的具体课次。“准备请假”仍算需要上课；“已请假”不再占用个人可安排时间。已请假的课次仍保留在服务端记录中，客户端的普通日程视图会隐藏它，不影响课程历史和其他周次。

保存活动并同时记录课次请假时，两部分在同一次数据库事务中完成，任何一部分失败都不留下半份修改。这里记录的是用户已经请假的事实，不代表软件向学校提交或批准了请假。

只作参考、不参加的活动可以保存为 `reserve_time=false`，用于保留通知，不占用本人时间。消息是否正式和本人是否参加要分别处理。

相关代码：[fixed_conflict_guard.py](../services/api/app/fixed_conflict_guard.py)、[agent_attendance.py](../services/api/app/agent_attendance.py)、[course_participation.py](../services/api/app/course_participation.py)。

## 4. 助手从提问到保存的过程

助手先查询用户已有记录，再调用工具准备修改。语言模型负责理解句子、寻找对象和组织回答；新增、改期、取消、排程等操作由服务端模块执行。

一次写入通常分四步：

1. 用户发消息。接口创建一条处理任务，返回任务编号，客户端继续查询进度。
2. 助手查询相关课程、日程或待办，生成一份修改预览。
3. 用户在界面核对并确认。文字消息里的“确认”不能绕过这一步。
4. 服务端重新检查当前记录，再把修改和保存结果一起提交。客户端收到成功结果后才显示“已保存”。

拒绝预览只取消这次待确认操作，不改变已保存的日程。包含多项内容的通知按组展示，用户可选择保存其中几组；所选内容一起检查、一起保存。助手不能为了安排个人学习任务，自动搬走课程或考试。

预览生成后，用户可能又在另一个页面改了任务或时间。服务端因此保留学期修改序号 `revision`，记录另有 `version`。确认时对照这些序号和当前内容；已发生变化就要求重新生成，不能把旧预览覆盖到新安排上。

客户端重试请求也不能重复新增。支持重试的接口使用 `Idempotency-Key`，助手消息使用 `request_id`。相同编号、相同内容返回已有结果；编号相同但内容不同会报错。

对话处理使用 LangGraph，处理进度保存在项目自己的数据库中。模型和工具连接在 [agent_runtime.py](../services/api/app/agent_runtime.py) 与 [agent_tools.py](../services/api/app/agent_tools.py)。删除对话会停止未完成的处理和待确认操作，但不会把这段对话已经保存的日程一并删除。

## 5. 撤销不是恢复整个数据库

撤销针对某次成功操作涉及的记录。比如把会议地点从 A301 改成 A302，撤销后恢复 A301，同时保留这次修改和撤销的历史。

撤销前也需要预览和确认。系统先检查相关记录有没有被继续修改，是否增加了相关提醒、进度或学习计划，以及恢复旧内容会不会和当前安排冲突。不能安全恢复时，给出原因并保持现状。

新建事项被撤销后，通常标为取消，并保留来源与历史；新增提醒被撤销后停用。撤销进度会让该条记录退出实际投入统计，不删除原记录。

学习计划另有检查：已经开始、被固定或继续修改过的时间块不能直接整批恢复；把重排前的时段恢复后会撞上后来新增的活动，也要拒绝撤销。前端不能为了让按钮“好用”而跳过这些检查。

实现见 [agent_undo.py](../services/api/app/agent_undo.py) 和 [schedule_api.py](../services/api/app/schedule_api.py)。

## 6. 接口和客户端对接

接口前缀为 `/api/v1`，登录后使用 `Authorization: Bearer <access_token>`。下表列出常用入口，全部参数以请求类为准。运行服务后可在 FastAPI 的 `/docs` 查看接口定义。

| 功能 | 主要接口 |
| --- | --- |
| 注册、登录、刷新登录 | `POST /auth/register`、`/auth/login`、`/auth/refresh` |
| 学期 | `GET /semesters`、`POST /semesters` |
| 课程导入核对、确认 | `POST /imports`、`POST /imports/{id}/apply` |
| 周课表、日历 | `GET /semesters/{id}/timetable`、`GET /semesters/{id}/calendar` |
| 待办 | `POST /items`、`PATCH /items/{id}`、`POST /items/{id}/lifecycle` |
| 日程冲突检查、保存 | `POST /events/conflict-preview`、`POST /events`、`PATCH /events/{id}` |
| 学习时间 | `GET /semesters/{id}/availability`、`PUT /semesters/{id}/availability` |
| 排程、重排预览 | `POST /semesters/{id}/plan-proposals`、`POST /semesters/{id}/replan-proposals` |
| 计划确认、固定时间 | `POST /plan-proposals/{id}/accept`、`PATCH /plan-blocks/{id}/lock` |
| 新对话、发送消息、查看进度 | `POST /agent/threads`、`POST /agent/threads/{id}/turns`、`GET /agent/runs/{id}` |
| 助手确认、拒绝、请求撤销 | `POST /agent/runs/{id}/decision`、`POST /agent/runs/{id}/request-undo` |
| 删除对话 | `DELETE /agent/threads/{id}` |

助手生成的学习计划必须从助手的确认入口保存，不能调用普通计划接口绕过确认。

常见错误处理方式：

| 状态码 | 客户端应该做什么 |
| --- | --- |
| 401 | 尝试刷新登录，仍失败再进入登录页 |
| 404 | 提示记录不存在，不显示其他账号的数据 |
| 409 | 安排或操作已变化，刷新后重新核对，不盲目重试旧内容 |
| 422 | 显示具体原因，补充需要的信息或明确处理冲突 |
| 429 | 提示稍后再试，避免连续提交相同排程 |

服务端错误包含 `code` 和 `message`。客户端负责展示可理解的中文；请求中的密码或完整拒绝内容不能原样放进错误日志。统一错误处理见 [main.py](../services/api/app/main.py)，请求与登录刷新见 [api.dart](../apps/mobile/lib/core/api.dart)。

## 7. 数据归属和开发时要保留的行为

服务端根据当前登录用户查询记录，不接受客户端自行指定另一个用户来访问。学期、课程、事项、计划等表带有用户关联，部分关联还使用包含用户编号的数据库外键。修改时同样检查归属，不能只凭记录编号更新。

客户端登录信息存放在安全存储中。切换账号会增加会话编号，旧账号尚未返回的请求会被忽略。离线课表缓存按账号分别保存，不能把上个账号的缓存带到下个账号。缓存只用于本机查看，不代表未联网的修改已经保存到服务端。

登录密码使用 Argon2 哈希；访问和刷新凭证在数据库中保存哈希。访问凭证有效期为 15 分钟，刷新凭证有效期为 7 天。退出时本机会清除登录信息；如果当时离线，不能保证服务端也已立即撤销该会话。相关代码：[auth.py](../services/api/app/auth.py)、[cache.dart](../apps/mobile/lib/core/cache.dart)。

修改这些模块时，应保留并检查以下行为：缺结束时间仍能保存；只处理真正冲突的课次；预览阶段不新增正式学习时间；重复确认不重复保存；失败时不留下半份修改；撤销不覆盖后续修改；切换账号不接收旧请求。

已有测试分别在 [test_event_conflict_guard.py](../services/api/tests/test_event_conflict_guard.py)、[test_agent_planning.py](../services/api/tests/test_agent_planning.py)、[test_agent_undo.py](../services/api/tests/test_agent_undo.py) 等文件中。

## 8. 登录和上传的可靠性

登录先验证密码，再锁定用户记录并重新读取密码哈希；如果验证期间密码被重置，这次旧密码登录会被拒绝。重置密码仍会删除已有会话。

刷新登录支持可选的 Idempotency-Key。同一次刷新在120秒内重试，可取回同一组令牌，不延长有效期；不同请求标识和过期重试不能使用旧刷新令牌。结果由旧随机凭据、服务端随机数和请求标识通过HMAC重新派生，数据库不保存明文令牌。客户端在发请求前保存请求标识，收到结果后再换成新凭据；迟到的旧令牌401只重试新令牌。

登录、注册、恢复账号分别统计IP额度，账号也有独立限制。刷新主要按会话限制；刷新和退出另有较宽的IP防刷额度，不与每分钟30次的登录额度共用。

两个上传入口都先完成请求读取和图片处理，再在线程中使用独立数据库会话保存。认证检查也及时关闭数据库会话，避免慢上传占着连接。配额按账号串行核对，课程和来源所属学期仍需验证。

加锁顺序与其他写入保持一致：有对话时先锁对话，再锁学期，最后锁账号。账号配额锁使用 PostgreSQL 的 `NO KEY UPDATE`，不修改账号主键，也不额外阻挡外键检查。上传等待学期时不能先占着账号锁，否则可能与标签或事项写入互等。

河南工业大学的节次随导入预览保存，确认导入时与课程在同一事务中应用；取消、过期预览或保存失败不会只改节次。其他学校和手工导入保留原有处理方式。
