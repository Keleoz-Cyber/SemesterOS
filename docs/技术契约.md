# 拾日开发说明

拾日把课程、个人日程、待办和学习计划放进同一个学期里管。Flutter 客户端负责展示和操作，Python 服务端负责保存、查冲突、排时间。助手用的是这些已有功能，它不另建一套日程，也不能凭聊天里一句回复就把数据改了。

这份文档给接手的人看。字段和接口的最终定义在代码里，这里讲的是那些从代码里一眼看不出来的约定，以及改了会出事的地方。

## 1. 项目里有哪几种记录

| 记录 | 表达什么 | 代码 |
| --- | --- | --- |
| 学期 | 名称、第一周周一、总周数、每天节次时间 | [academics.py](../services/api/app/academics.py) |
| 课程 | 哪几周、周几、第几节；展开成某一天的具体课次 | [occurrences.py](../services/api/app/occurrences.py) |
| 日程 | 会议、彩排、比赛这类活动，可以只有日期或只有开始时刻 | [calendar_events.py](../services/api/app/calendar_events.py) |
| 事项 | 作业、待办、考试。待办带剩余耗时，考试用自己的考试时间 | [items.py](../services/api/app/items.py) |
| 学习时间 | 每周愿意学的时间，加上临时不可用的时段 | [planning.py](../services/api/app/planning.py) |
| 学习计划 | 给某个任务安排的一段具体时间，能固定也能取消 | [schedule_api.py](../services/api/app/schedule_api.py) |
| 助手对话 | 用户消息、处理过程、待确认的修改、保存结果 | [agent_api.py](../services/api/app/agent_api.py) |

有两组东西经常被混为一谈，这里先说清楚。

第一组：「任务还要做 60 分钟」和「今晚给它安排了 60 分钟」是两件事。排进日历不等于做完，所以存计划的时候不会自动扣剩余耗时，实际进度得用户另外记。

第二组：「整门课」和「具体某一次课」。调课、停课、请假都是对某一次课操作的，不能靠删掉整门课来代替。

表结构在 [models.py](../services/api/app/models.py)，请求字段在各模块的 `*_schemas.py` 里，连接在 [database.py](../services/api/app/database.py)，迁移在 `services/api/alembic/`。

## 2. 时间是怎么存的

日期和学期周次一律按上海时区解释。带具体时刻的必须带时区，进来之后转成 UTC；只有日期的还是日期，不给你补成当天午夜——补了就等于凭空造了一个截止点。

时间记录分两层：一层说知道多精确，一层说这个时间是干什么用的。

| 用户说法 | 存成什么 | 后面怎么用 |
| --- | --- | --- |
| 明天 9 点开会，几点结束不知道 | 具体开始时刻，结束留空 | 能存；检查 9 点撞不撞课，但不假定全天开会 |
| 周五交材料 | 日期 | 能存；不擅自推成周五 23:59 |
| 第 12 周考试 | 周次 | 能存；不把整周都算成考试占用 |
| 10 日到 12 日办理 | 日期范围，标为办理窗口 | 是可办理范围，不等于连续三天都不能排别的事 |
| 周六全天外出 | 日期，标为全天 | 按用户明说的全天占用处理 |
| 有空记得整理资料 | 时间未知 | 存成待办，不逼着选日期 |

「预计周五」和「周五」的差别不在有没有钟点，而在话说得肯不确定。记录里用 `certainty` 表确定程度，`time.precision` 表精度，`time.meaning` 区分截止、开始、办理窗口、候选日期、全天这些用途。

待办允许不填耗时、开始时间、截止时间。只有要自动排学习时间了，才需要这些信息：

- 剩余耗时不知道，就算不出该排多少分钟，先补。
- 普通任务没写等待条件，就可以在本次规划范围里开始，不用挨个问「你几点能开始」。也别为了排程把原记录改成一个虚构的开始时刻。
- 明确说了「等审批结果出来再做」，这个条件必须原样保留，不能按立即可做处理。
- 没截止时间的任务照样能排，用用户选的规划范围。为了排程捏一个截止时间是不行的。

字段检查在 [item_schemas.py](../services/api/app/item_schemas.py)，开始条件在 [task_readiness.py](../services/api/app/task_readiness.py)。

## 3. 保存前怎么查冲突

手动表单和助手保存走同一套冲突检查。新增或者改时间的时候，比的是修改前后——只找这次新冒出来的冲突和受影响的学习计划，历史上的重叠不翻旧账。

举个例子。课是 8:00—9:50，用户加一个 9:15 开始的会。这会有没有结束时间都不影响判断：9:15 那一刻既要上课又要开会，所以得在保存前让用户处理。可以改时间，可以给具体那一次课记一笔「已请假」，也可以明说就是要重叠。

换成会只说 7:30 开始、没说几点结束，那就不能断言 8 点的课一定冲突。系统保留「结束时间没说」这个提示，但不会要求请掉当天所有课。原文明确要求提前到场的，已知的提前到场时间也要算进检查。

请假只记用户选中的那几次课。「准备请假」仍然算要上课，「已请假」才不再占个人可安排时间。已请假的课次在服务端记录里还在，客户端的普通日程视图把它藏起来，课程历史和其他周次照旧。

保存活动的同时记课次请假，这两步在同一个事务里，任何一步失败都不会留下半份修改。这里记的只是「用户说自己已经请假了」，不代表软件替谁向学校提交或批准了请假。

只作参考、人不去的活动可以存成 `reserve_time=false`，用来保留通知，不占本人时间。消息正不正式和本人去不去是两件事，得分别处理。

相关文件：[fixed_conflict_guard.py](../services/api/app/fixed_conflict_guard.py)、[agent_attendance.py](../services/api/app/agent_attendance.py)、[course_participation.py](../services/api/app/course_participation.py)。

## 4. 助手从提问到保存

助手先查用户已有的记录，再调工具准备修改。模型负责理解句子、找对象、组织回答；新增、改期、取消、排程这些实际动作由服务端模块执行。

一次写入分四步：

1. 用户发消息，接口建一条处理任务，把任务编号返回给客户端，客户端拿编号轮询进度。
2. 助手查相关课程、日程、待办，生成一份修改预览。
3. 用户在界面上核对、确认。聊天里打「确认」不能绕过这一步。
4. 服务端重新检查当前记录，把修改和保存结果一起提交。客户端收到成功才算「已保存」。

拒绝预览只取消这次待确认操作，已保存的日程一个字都不动。一条通知里有多件事，按组展示，用户挑几组存几组，选中的一起检查、一起保存。助手也不许为了给个人学习腾地方，自动把课程或考试搬走。

预览生成之后，用户可能在另一个页面把任务或时间改了。所以学期上有修改序号 `revision`，记录上另有 `version`。确认的时候对照这两个和当前内容，发现变过就要求重新生成，绝不能把旧预览盖到新安排上。

客户端重试也不能重复新增。支持重试的接口用 `Idempotency-Key`，助手消息用 `request_id`。编号一样、内容也一样，返回已有结果；编号一样但内容不同，报错。

对话处理跑在 LangGraph 上，进度存在项目自己的库里。模型和工具在 [agent_runtime.py](../services/api/app/agent_runtime.py) 与 [agent_tools.py](../services/api/app/agent_tools.py)。删对话会停掉没做完的处理和待确认操作，但那段对话已经存下的日程不会被一起删。

## 5. 撤销不是回滚整个库

撤销只针对某次成功操作碰过的那些记录。把会议地点从 A301 改成 A302，撤销后回到 A301，同时这次修改和撤销本身都留在历史里。

撤销也要先预览、再确认。系统先看相关记录有没有被继续改过，有没有多出关联的提醒、进度、学习计划，以及恢复旧内容会不会跟现在的安排撞上。不能安全恢复就说清楚原因，然后保持现状。

新建的事项被撤销，一般标成取消，来源和历史都留着；新增的提醒被撤销就停用。撤销一条进度，会让它退出实际投入统计，但不删原记录。

学习计划还多几道检查：已经开始、被固定、或后来又改过的时间块，不能整批恢复；把重排前的时段恢复回去会撞上后来新增的活动，同样得拒绝。前端不能为了按钮好按就把这些检查跳过。

实现见 [agent_undo.py](../services/api/app/agent_undo.py) 和 [schedule_api.py](../services/api/app/schedule_api.py)。

## 6. 接口和客户端

前缀 `/api/v1`，登录后带 `Authorization: Bearer <access_token>`。常用入口在下面这张表，参数以请求类为准。服务跑起来后 `/docs` 里有完整定义。

| 功能 | 主要接口 |
| --- | --- |
| 注册、登录、刷新 | `POST /auth/register`、`/auth/login`、`/auth/refresh` |
| 学期 | `GET /semesters`、`POST /semesters` |
| 导入核对、确认 | `POST /imports`、`POST /imports/{id}/apply` |
| 周课表、日历 | `GET /semesters/{id}/timetable`、`GET /semesters/{id}/calendar` |
| 待办 | `POST /items`、`PATCH /items/{id}`、`POST /items/{id}/lifecycle` |
| 日程冲突检查、保存 | `POST /events/conflict-preview`、`POST /events`、`PATCH /events/{id}` |
| 学习时间 | `GET /semesters/{id}/availability`、`PUT /semesters/{id}/availability` |
| 排程、重排预览 | `POST /semesters/{id}/plan-proposals`、`POST /semesters/{id}/replan-proposals` |
| 计划确认、固定 | `POST /plan-proposals/{id}/accept`、`PATCH /plan-blocks/{id}/lock` |
| 新对话、发消息、看进度 | `POST /agent/threads`、`POST /agent/threads/{id}/turns`、`GET /agent/runs/{id}` |
| 助手确认、拒绝、请求撤销 | `POST /agent/runs/{id}/decision`、`POST /agent/runs/{id}/request-undo` |
| 删对话 | `DELETE /agent/threads/{id}` |

有一条容易走岔：**助手生成的学习计划只能从助手的确认入口存**，不能调普通计划接口绕过去，绕了就等于没有确认。

错误怎么处理：

| 状态码 | 客户端做什么 |
| --- | --- |
| 401 | 先试刷新登录，还不行回登录页 |
| 404 | 说记录不存在，别顺手显示别人的数据 |
| 409 | 安排或操作已经变了，刷新重核，别闷头重试旧内容 |
| 422 | 把具体原因显示出来，补信息或者处理冲突 |
| 429 | 提示稍后再试，别连着提交同一个排程 |

服务端错误体是 `code` 加 `message`。中文提示由客户端负责，请求里的密码、完整拒绝内容不许原样进错误日志。统一错误处理在 [main.py](../services/api/app/main.py)，请求和刷新在 [api.dart](../apps/mobile/lib/core/api.dart)。

## 7. 数据归属和不能改坏的行为

服务端按当前登录用户查记录，不接受客户端自己指定一个用户编号。学期、课程、事项、计划这些表都带用户关联，部分还用了带用户编号的复合外键。改的时候同样要校验归属，不能光凭记录编号就更新。

客户端登录信息放安全存储。切账号时会换会话编号，旧账号还没回来的请求直接丢掉。离线课表缓存按账号分开存，上个账号的缓存绝不能带到下个账号。缓存只管本机能不能看，不代表没联网的修改已经存到服务端。

密码用 Argon2 哈希，访问和刷新凭证在库里存的也是哈希。访问凭证 15 分钟，刷新凭证 7 天。退出时本机会清掉登录信息；如果当时离线，服务端有没有立刻撤销那个会话是不保证的。相关代码：[auth.py](../services/api/app/auth.py)、[cache.dart](../apps/mobile/lib/core/cache.dart)。

动这些模块之前，先记住这几条行为，测试里也都盯着：

- 缺结束时间照样能存
- 只处理真正冲突的课次
- 预览阶段不写正式学习时间
- 重复确认不会存两遍
- 失败不留半份修改
- 撤销不覆盖后续修改
- 切账号不接收旧请求

对应测试在 [test_event_conflict_guard.py](../services/api/tests/test_event_conflict_guard.py)、[test_agent_planning.py](../services/api/tests/test_agent_planning.py)、[test_agent_undo.py](../services/api/tests/test_agent_undo.py) 等。

## 8. 登录和上传的可靠性

登录先验密码，再锁用户记录、重新读一次密码哈希。为什么多读这一次？因为验证期间密码可能被重置，读了才能拒掉这次旧密码登录。重置密码顺手删掉已有会话。

刷新登录支持可选的 Idempotency-Key。同一个刷新在 120 秒内重试，能取回同一组令牌，有效期不延长；换个请求标识或者过期了还拿旧刷新令牌来，不认。结果由旧随机凭据、服务端随机数、请求标识三者 HMAC 重新派生，库里不存明文令牌。客户端发请求前先存请求标识，拿到结果再换成新凭据；迟到的旧令牌报 401 时只重试新令牌。

登录、注册、恢复账号分别按 IP 统计额度，账号自己也有限制。刷新主要按会话限，刷新和退出另有较宽的 IP 额度，不跟每分钟 30 次的登录额度共用一池。

两个上传入口都是先把请求读完、图片处理完，再在线程里用独立的数据库会话保存。认证检查也会及时关掉数据库会话，免得一个慢上传把连接占着。配额按账号串行核对，课程和来源所属的学期仍然要验。

加锁顺序跟其他写入保持一致：有对话先锁对话，再锁学期，最后锁账号。账号配额那把锁用 PostgreSQL 的 `NO KEY UPDATE`，不改账号主键，也不额外挡外键检查。上传等学期的时候不能先占着账号锁，不然可能跟标签或事项的写入互相等死。

河南工大的节次随导入预览一起存，确认导入时和课程在同一个事务里应用。取消、预览过期、保存失败，都不会出现「节次改了课程没进来」这种半截状态。别的学校和手工导入保持原来的处理方式。

## 9. 标签：推荐、自动合并、关联查询

1.1.1 的标签处理跟模型理解是分开的两件事。`tag_classifier.py` 用 `data/tag_rules.json`，移动端那份 `tag_rules.g.dart` 由 `scripts/generate-tag-rules.py` 生成，两边共享标准名、用途分组和词语匹配规则。

判断主要看标题和关联课程，备注或短来源拿来补类别，不把长通知里提到的所有主题都往每条记录上塞。新建时忽略模型自己编的标签，用户直接指定的自定义标签可以留；保存时统一成标准名。普通编辑保留没被明确改过的分类和标签。

`POST /tags/organize` 在账号内整理已有名称，比如组会、班会、座谈会归到会议，彩排、联排归到排练。它按顺序先锁该账号的学期，再锁账号，然后调资源的标签 ID、版本、学期修订，并写审计记录。旧 ID 和旧名字靠合并和别名继续能解析，用户显式自定义改过的按已有映射走。重复整理没新变化，就不再加版本号。

`GET /tags` 只读，返回用途分组、使用次数、示例和别名。客户端进标签页会自动调一次整理接口，但不弹「已完成」的提示——没变化还要弹一下很烦。万一碰到旧服务没有整理接口，可以按既有的预览与应用接口把标准名迁过去；正式服务现在有新接口。

`GET /tags/{tag_id}/records` 返回当前账号真正关联的事项和日程，包括别的学期、已完成、已取消的记录，支持 offset/limit 分页。旧标签 ID 解析到保留的那个，单条资源去重；不属于这个账号的标签返回 404。响应里只放列表要的摘要和学期信息，详情还是调原来的事项或日程接口。

跨学期看详情用的是对应学期的操作会话，不会把主界面所选学期改掉。客户端要核对账号、登录会话和范围，切过去之后迟到的结果丢掉。主要测试是 `test_tag_classifier.py`、`test_tag_auto_organize.py`、`test_tag_records.py` 和移动端的 `tag_*_test.dart`。

## 10. 其余功能和系统协作

| 内容 | 实现与约定 |
| --- | --- |
| 首页、空档建议 | `briefs.py`、`centers.py`；个人显示设置、当天忽略建议、页面状态存在移动端 |
| 资料和学习偏好 | `user_profiles.py`；资料、每周学习、休息、前后缓冲参与相关计算 |
| 统一搜索 | `personal_data.py`；按账号和学期查课程、日程、事项、来源文字，校验类型和分页 |
| 统计 | `insights.py`；范围、分类、标签、进度，时长合计、去重占用、未知时长分开算 |
| 进度 | 存用户记的实际用时、剩余、完成状态；排程不自动扣任务剩余工作 |
| 预览就地编辑 | `preview_editing.py`；重校字段、来源和冲突，编辑也不能绕过确认 |
| Android 卡片和跟踪 | 客户端把同步数据交给 `DeviceSurfaces.kt`，系统组件显示；不是服务端推送 |
| 本地提醒 | 同步账号提醒后交给系统；离线延后只读本机已知记录，完成仍要服务端看 |
| 导出与注销 | `/me/export` 走字段白名单，`/me/erase` 要密码加明确文字，附件交给清理队列 |
| 用户反馈 | `/me/feedback` 写进所属账号；普通客户端没有查全部用户反馈的接口 |

进行中通知要用户手动开。知道结束时间就倒计时，不知道就显示已经开始多久，最多跟 12 小时。Android 16 的增强展示最终长什么样是系统说了算。桌面卡片、系统通知、Flutter 进程各干各的，没有为了保活加常驻服务。

接口总表见[接口索引](接口索引.md)，客户端入口和实现对应见[功能清单](功能清单.md)。
