# 首轮体验反馈与重设计建议

日期：2026-09-21。依据：用户提供的 `findings1.docx` 全部文字与 7 张截图，以及当前仓库的静态代码核查。

本文是问题整理与设计建议，不是已经批准的开发方案。本轮不修改 App、接口、数据库或线上服务，不制作比赛演示。此前模拟器连接本地后端的问题，按用户要求不纳入此清单。原 Word 文档保持不变。

主要结论：这次需要重新设计页面的信息顺序、常用操作路径、AI 输入与执行流程，并补齐固定日程能力。视觉与动效也要整体调整。已有的课表导入、提醒、规划算法、来源记录与确认机制可以复用，但需要逐项核查接口和状态管理能否支持新流程。

## 用户补充的产品定位

后续进展：用户已授权V2整体方案、关键页面原型和技术选型／改造清单，对应17／18／19文档；尚未授权在这一轮实施App重构。技术原则为成熟能力优先、实际体验决定取舍，新工具先验证，不为了自研重复实现通用能力。

用户进一步明确：生活中经常收到临时通知，希望便捷地汇总到一个 App 中，与课表一起直观查看；很多操作应能用一句话或语音完成；AI 要结合自己的全部日程进行分析，并提供建议和评价。

这段补充是后续重设计的核心依据。上文及后文的页面方案仍是建议，若与此定位冲突，应重新调整，不能因为已有代码或旧设计而限制产品方向。

产品主线应是：**通知进入 → 理解并整理 → 与课表合并呈现 → 提醒与执行 → 根据变化调整 → 分析与反馈**。核心价值是减少整理成本，并让用户看清整体安排、及时作出决定。课表是重要时间背景，临时通知与其他个人日程也是主要内容。

### 用户已经明确的方向

- 临时通知是高频输入，应该与课程出现在同一套可浏览的日程中。
- 文字和语音是主要快捷操作方式，用户不必先学习 App 的内部功能分类。
- AI 应结合整体日程分析，能力不止于录入时提取字段。
- 建议和评价需要成为日常使用的一部分，服务于安排时间、处理变化与回顾执行。

### 据此提出的设计建议

1. **统一呈现，保留不同时间含义。** 课程、组会、活动按开始与结束时间展示；作业等按截止时间展示；个人学习计划展示可调整的时间块；日期不明确的通知保留待确认状态。不能把截止时间误画成活动时段，也不能把会议当成可任意搬动的任务。
2. **一句话跨越功能入口。** “周三五点开组会”“报告改到周五交”“今晚有事，帮我调整一下”“这周什么时候能复习”应从同一入口处理。系统识别新增、变更、安排或询问，展示必要的核对与结果；仅在确实存在关键歧义时追问。
3. **通知变化可追溯。** 保留原通知依据，识别可能重复的通知与后续更改，明确改的是哪条安排。重复识别、连续语境、批量通知等仍需单独设计，不视为已有能力。
4. **整体分析输出可执行建议。** 根据课程、活动、截止事项、已有计划及用户设置的可用时间，指出冲突、连续忙碌、截止集中和可用空档，并给出能直接核对、采纳或调整的建议。分析页面不以堆图表为目标。
5. **评价要有依据。** 区分“日程安排得是否合理”和“用户实际完成得如何”。前者可依据现有日程分析；后者需要完成或进度记录，不能将计划时间当成真实投入，也不能把未记录等同于未完成。
6. **主动帮助要控制打扰。** 新通知造成冲突、临近截止且时间不足时及时提示；普通建议就地呈现，不让每次打开 App 都弹出长篇评价。
7. **重新评估页面命名。** 若当前“课表”页承载课程之外的完整日程，可考虑改为“日程”，课表作为其中一种视图。是否更名及底部导航如何分工，留待原型验证，尚未定案。

后续验收应围绕一个完整场景：用户收到组会通知，说一句话便得到待确认的安排；确认后它与课程一起出现；系统说明是否撞课或挤占个人计划；用户可直接接受调整建议；后续时间变更可用一句话更新，关联提醒和分析保持一致。

### 用户进一步提出的 Agent 方向

用户希望 AI 像 Agent 一样能够使用 App 的能力：用户提出问题或需求，AI 自行查询、分析和操作，最终交付结果。此处记录为产品方向，尚未授权开始实现。

静态核查确认，当前 AI 主要采用“单次模型请求 → 结构化意图或字段 → 预设流程”的方式。已有修改任务、修改提醒、请求排程及确认应用能力，所以并非只有对话接口；但操作提示词明确不提供事项列表、不推断目标，一次多个修改要求拆开，多种操作被排除，尚不具备统一的多步工具执行与连续语境处理流程。

建议把 App 现有业务能力开放为受账号权限约束的内部工具，由 Agent 按需求组合使用。首批能力覆盖查询日程与来源、查找事项、检查空档与冲突、生成建议、准备新增或修改、生成排程及提交已授权改动。通过业务工具操作数据；需要用户查看详情时导航至对应页面，不以模拟点击按钮作为主要实现。

目标执行流程：理解需求 → 按需查询真实状态 → 选择工具 → 执行并读取结果 → 根据结果继续或纠正 → 向用户展示回答、预览或已完成的变更。只读查询直接给答案；具体明确且已获授权的低影响修改，可研究直接完成并提供撤销；歧义、较大范围重排或涉及现实安排的变化，给出简洁预览后确认。最终确认粒度需要在设计中明确，不机械地让每一步都确认。

智能程度以能完成多少真实场景衡量，而不是是否有聊天框或是否调用模型 API。需要新增多轮对象引用、工具参数校验、执行结果核对、失败恢复、重复提交防护及可回看记录；复用现有业务权限与版本校验。不得仅凭模型生成一段“已完成”就展示操作成功。

“用户问都能给出结果”应落为产品范围内尽量闭环：有数据则回答，有工具则执行，需要选择则提出具体选项，缺信息或暂不支持则准确说明缺什么并保留已有进展。不能承诺未知事实、尚未接入的外部服务或没有权限的操作同样可以完成。

## 1 证据与判断的边界

- **已确认**：截图直接显示，或代码能确认的行为与结构。
- **体验反馈**：用户实际使用感受，必须作为后续验收场景；截图和静态代码不能测出具体耗时或帧率。
- **待验证**：可能的原因，尚未复现或取得运行证据。
- **建议**：供下一轮设计选择，不视为用户已确认的需求细节。

## 3 需要修正或补充的判断

### 首页应优先展示课程，但不承诺任何情况下都不滚动

目标是打开后马上看到“今天有什么、下一件是什么、现在需要处理什么”。建议标准字号、普通手机上，常见的 3 至 4 次课程用紧凑列表展示，避免大横幅把课程挤到首屏外。课程特别多、小屏或大字号时仍允许滚动，不能靠缩小字和点击区域强行塞满。

已结束课程可降低视觉强度，但不应无提示地消失。下一节课程强化时间和地点；临近截止事项不能全部沉到自定义模块后面。

### 不同页面要有变化，但操作规则仍需一致

赞同取消所有页面套同一个教学楼横幅。建议今日以紧凑时间线为主、课表以网格为主、计划以可执行安排为主、学期以节点与周带为主。字体、间距、主次按钮、风险含义仍应一致，避免每页都要重新学习。

### 动效应让操作连续，不能用来掩盖等待

优先设计周次切换、日期展开、抽屉拉起、任务完成、方案差异出现及导航状态的动效。避免让每张卡片一直漂浮或闪烁。允许减少动态效果；等待时间长时展示真实阶段，不使用虚构百分比。持续卡顿的定位与修复应先于大量增加动画。

### 分段切换不是天然高成本，当前上下文衔接不足才需要重做

“周课表／按天查看”的显式控制可以保留为可发现入口。选中周课表的一天后，展示这一天的完整列表，而不是突然换成整周大卡片。切换时保留周次、选中日期和必要的滚动位置。

现有周网格横向滚动用于查看完整七天，不能直接把同一手势又定义为切周。建议先用顶部周带与选周面板切换；若增加横滑切周，需先解决网格水平浏览的手势冲突。

### “云同步提示”里有部分其实是说明文案

截图中“任务显示在截止日期所在周”等内容是使用说明，并不表示正在同步。误解来自所有普通说明都配云图标。需要调整提示语义和位置，而不仅是改颜色。首次使用的解释可收进帮助或就地提示，真正的持续失败则应提供明确操作。

## 4 四个页面的建议分工

| 页面 | 主要回答的问题 | 建议首屏内容 | 延后或移走的内容 |
| --- | --- | --- | --- |
| 今日 | 我今天先做什么，接下来去哪 | 小日期栏、下一项安排、紧凑的今日课程、紧急事项 | 品牌大横幅、独立占位的统计大卡、长篇分析 |
| 课表 | 哪一天有课，哪里有空档 | 紧凑周次栏、课程网格、选中日详情 | 普通事项管理按钮、与首页重复的大课程卡列表 |
| 计划 | 要完成什么，安排在哪，哪些需调整 | 待办与已安排内容的关系、下一段个人计划、冲突或风险 | 重新计算按钮、多个等权重的生成入口、重复学习时间设置 |
| 学期 | 重要节点在哪，未来哪周更忙 | 当前周定位、学期概览、考试及截止节点 | 从第一周开始逐个堆叠的空面板、管理功能的主视觉 |

首页自定义建议是“有限组件”：近期截止、今日个人计划、可用空档、近期考试等可排序或隐藏。先给可直接使用的默认布局；不要求新用户先搭建首页。组件入口跳转后要继承相关日期和事项上下文。

底部导航必须连同全局输入入口一起出原型。可保留四个信息目的地，重新设计选中态和布局；全局输入只有一个主要位置，解决目前悬浮按钮遮住课程的问题。不把“保留四个目的地”理解为只换图标。

## 5 统一智能输入与确认流程

建议的操作路径：打开统一入口 → 输入文字或添加语音、图片 → 系统判断意图与关联对象 → 展示可编辑的结果 → 用户确认 → 更新相应页面。

输入抽屉首先是输入区域，不再先询问“作业还是考试”“新增还是修改”“新建计划还是最小扰动重排”。可以提供两三个短示例，如“周五交实验报告”“今晚没做完的帮我调整”。媒介入口用图片、语音图标呈现，手动填写保留为低层级兜底。

系统识别结果分为新增事项、修改事项、调整提醒、记录现实变化和安排个人计划。默认复用已有上下文，只有多个对象都可能匹配、时间确实不足等情况才追问，并保留已经识别出的内容。日常一句话不应被迫进入完整表单。

规划预览应直接说明安排了什么、移动了什么、为什么，以及未能安排的内容。普通用户不需要先选择算法模式。新增课程占用等现实变化与个人计划调整仍分别可确认，不能因为合并入口就把两种行为悄悄绑在一起。

“用户确认”也应与改动规模匹配：单项操作一张简洁确认卡；多项操作按组核对；重要变更展示前后差异。来源、缺失信息、撤销与手动操作继续保留。AI 不可用时仍能查看课表和手工记录。

## 6 组会通知暴露的能力缺口

示例含义是“本周三 17:00—18:00 开组会，地点或会议室编号 6412”，其中还提及让某位同学约会议室。

合理结果应先展示“组会”固定日程候选，有明确开始与结束时间，并让用户核对 6412 的含义。若按截图显示的原消息时间 2026-09-21、北京时间解释，则“本周三”是 2026-09-23；日期依据仍应可查看与修改。

不能自动把通知中指派给别人的“约会议室”变成当前用户的任务。如果需要，提供“也记录预约会议室待办”的可选操作；不能声称已经替用户完成真实预约。

代码确认的限制：

- `ItemFields.kind` 只有 `assignment/task/exam`。
- `ItemFields` 禁止非考试事项携带 `end_at`，普通会议不能忠实表达完整占用区间。
- 当前文本提示词要求一次只处理一个事项。
- 文本确认页对部分非新增意图仍引导用户换入口，没有完全承接统一处理。
- 结构、证据片段、课程归属等多种校验失败都返回同一“内容还不完整”提示。该截图本身无法定位是哪一种失败。

建议增加一般固定日程能力，适用于组会、社团活动、答辩、面试、就诊等，并与可安排的作业／任务明确区分。已确认的固定日程应进入冲突检测、时间占用、提醒、今日与按天查看等流程；不能自动作为可移动的个人任务重排。

这是涉及数据模型和全链路行为的改动，不是只新增一个类型选项。需要评估存储迁移、API、来源与版本、提醒、取消与修改、排程器、余量计算、缓存和旧客户端兼容。考试继续保留考试专属规则，不用“考试”类型冒充会议。

本轮没有重新向模型发送原通知，没有查看私人服务日志，因此不声称已复现或确定失败根因。后续应先用匿名等价样例复现，再记录脱敏的错误类别和请求标识，避免用笼统错误挡住诊断。

## 7 加载与流畅度

### 代码中已经看到的路径

主页面按当前 Tab 构建一个页面子树，没有保留所有 Tab 的完整状态。学期页 `HubData` 在 `initState()` 发起查询，内部数据初始为空，并每 45 秒发起一次更新。切出再切回会重走初始加载路径，这可以解释“为什么每次都等”，但不能证明具体等待一秒，也不能据此认定它导致全局掉帧。

`ItemsController.refresh()` 会重新获取事项、课程与提醒，接着同步通知、读取计划并刷新风险；公共刷新还会调用课表或会话更新。要分清哪些是用户看到内容前的必要请求，哪些可以延后或只在数据变更时处理。

### 后续验证与设计原则

- 分别测量首次打开、再次切回、切周、长列表滚动、键盘与抽屉出现、AI 等待和保存后的反馈。
- 用真机 profile 模式分析帧耗时；debug 模式及模拟器数据不作为正式性能结论。这与 [Flutter 官方性能诊断说明](https://docs.flutter.dev/perf/ui-performance) 一致。
- 保留可安全展示的课表和事项数据、浏览位置，后台更新变化部分；不要为每次返回都重新铺满加载画面。
- 风险和排程结果需继续核对版本与有效期。旧课表可标记为缓存展示，失效风险值不能伪装成当前结论。
- 分开记录网络延迟、服务端耗时、UI 重建和光栅耗时。没有数据前不把原因归到服务器、动画、插图或 Flutter 本身。
- 后续为代表性真机建立帧时间与页面恢复基线，再设定可验收指标。本轮不虚报帧率或修复效果。

## 8 有价值的新内容与素材

建议先选少量与现有安排直接有关的内容：

1. **课间可用空档**：说明扣除已记录课程和固定安排后还剩多少时间，结合用户设置的休息缓冲提出短任务候选；不自动认定空白时间都可学习。
2. **本周节奏概览**：展示课程较密集的天、任务集中截止的天，点击后进入对应日期与调整建议。
3. **近期可处理的一件事**：根据明确截止、耗时和可用时段提出具体下一步，用户可直接接受或跳过。

这些计算尽量使用已知数据与确定性规则，AI 用于解释和理解意图。暂不增加没有依据的情绪判断、学习人格、效率排名或大量生成式图表；没记录的学习时间不能算成真实投入。

素材需求等版式确认后再提交给用户：品牌图标候选、少量不同情境的空状态插画、必要的引导素材。每项给出用途、尺寸、透明背景要求、色彩与是否预留动效空间。普通按钮图标和排版无需全部生成图片；本轮不要求用户先准备一堆素材。

## 9 建议推进顺序与验收场景

以下是工作顺序建议，不含日期排期，也不代表现在开始实现。

1. **整理并确认体验方向**：本文件为当前记录，后续反馈继续补充；先解决页面分工、统一输入和固定日程语义。
2. **核查关键行为与建立性能基线**：匿名复现组会解析，测量重复加载和掉帧，为后续改动保留可比较证据。
3. **输出可审阅原型**：四个主页面、底部导航、统一输入及结果确认、学校选择，包含关键过渡状态；确认后再修订 01／02／03 相关设计。
4. **补齐模型与状态管理**：一般固定日程、统一意图处理、页面数据复用、刷新与有效性边界。数据库变更要考虑已安装客户端。
5. **成套实现 UI 与交互**：按完整流程替换，共享规范处理间距、入口、提示与动效，不逐页追加临时按钮。
6. **真机闭环验收**：逐条回看本清单，覆盖失败、空数据、大字号、长名称与弱网场景。

重点验收场景：

- 打开今日页面，常见课程数量下无需先越过大幅装饰即可看到当日安排；极端内容仍清晰可浏览。
- 一句话记录组会，得到时间区间的固定日程，不误把他人职责记到自己名下。
- 一句话调整提醒或今晚未完成的计划，不要求用户先选择内部操作类别。
- 调课通知先确认现实变化，个人计划调整另有可理解的预览，固定安排不被自动搬动。
- 来回切换学期页，已有内容与浏览位置稳定保留；变化数据在后台更新，失效分析不冒充最新结论。
- 同一个屏幕不重复提供相同目的的入口；常用主操作数量受控，错误恢复入口在需要时出现。
- 单校已适配、多校可扩展，未适配学校状态如实表达。
- 动效帮助理解变化，主要浏览与输入过程在代表性真机上通过性能核查。
