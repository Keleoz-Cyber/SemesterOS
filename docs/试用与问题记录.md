# 试用意见与问题记录

对应版本 1.1.1，2026-10-17。

## 这些意见是怎么来的

用户给过我 16 段学生口吻的反馈文字，覆盖不同年级，也提到班委、学生会、考研、竞赛这些场景。话是像学生说的，但我没法证实这是 16 个彼此独立的人写的——没有持续使用的日志，没有问卷，也没有统一的访谈记录。所以下面只整理意见本身，不拿它算人数、留存、满意度、提效比例。这些数要真给，得另做研究，不能从一堆聊天文字里数出来。

| 主题 | 反馈里提到什么 | 现在是什么情况 |
| --- | --- | --- |
| 通知转日程 | 群消息、截图省了重打，但日期还得自己对 | 保留识别文字和原文，能就地改预览，保存要确认 |
| 新手入口 | 功能太多，不知道先干哪件 | 说明按课程、通知、任务分开了；手动记录可以先只填必填项。真实新用户怎么上手还没观察过 |
| 学校适配 | 没适配的学校导不进来 | 现在两所，其他走手动录入；加学校要页面样本和回归 |
| 估时与执行 | 实际比预估久，临时的事一来计划就乱 | 有进度记录、剩余工作调整、固定块和重排；按个人历史学估时和自动复盘都还没做 |
| 请假理解 | 把“已请假”当成已经向学校申请成功了 | 文案写的是“只记录已经办好的具体课次”，已请假的课次从当前日程里隐掉 |
| 系统入口 | 想在桌面直接看到下一节课 | 有桌面卡片和用户自己开的进行中通知；各家厂商设备上的表现还得继续看 |
| 手动和 AI | 小事手动更快，复杂的通知才适合扔给助手 | 手动新增、编辑、批量操作都留着，助手和手动用的是同一份记录 |
| 使用习惯 | 有人本来就没记日程的习惯，用几天就不开了 | 得靠访谈和使用日志找原因，不能凭“功能不少”就推断用户需要 |
| 使用阶段 | 高年级更关心面试、毕设 | 日程、任务、考试、期限能放一处记，具体好不好用还得验 |
| 标签 | 同类名字一堆，找不到相关的事 | 1.1.1 会自动归并同类标签，点标签能看跨学期记录 |

## App 里的反馈

入口在“账户 → 反馈问题”。填问题类别、当时在做什么、实际发生了什么、期望怎样，加上 App 版本。开发者用 `scripts/view_feedback.py` 看服务器上的记录，用法在[维护说明](部署与维护.md)。现在没有工单状态，应用内也不会回你。

想让我能查，提交时尽量写全：版本、手机和系统、从哪个入口进的、输入的原话（先脱敏）、实际结果、期望结果、发生时间、能不能复现。如果是模型理解错了，最好附上保存后的字段或者那张预览；如果是提醒没响，还得说权限、系统电池设置、有没有强行停止过。

## 以后做验证怎么记

| 字段 | 要填什么 |
| --- | --- |
| 样本与同意 | 匿名编号、怎么招的、愿不愿意被引用 |
| 环境 | App 版本、系统、设备、网络、权限 |
| 场景 | 原始输入、已有课程或任务、这次想干什么 |
| 观察 | 实际步骤、核对和改错花的时间、成了还是没成 |
| 后续 | 问题编号、修复版本、复验结果 |

引用原话就保留原意，动过哪里要说明；碰到姓名、群聊、账号先脱敏。合成的模拟器场景、用户随口给的意见、正式的用户研究，这三类分开记，别攒在一张表里当同一份证据用。
