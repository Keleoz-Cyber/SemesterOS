# 测试与参赛准备

测试要分别回答两个问题：程序是否按规则处理数据，用户是否能在实际界面上完成操作。后端测试通过不能代替界面操作，模拟器操作成功也不能代表所有手机都表现相同。

## 1. 日常开发测试

后端依赖安装好后，可以从仓库根目录运行：

```powershell
.\services\api\.venv\Scripts\python.exe -m pytest services/api/tests -q
```

多数用例使用临时SQLite。涉及PostgreSQL行锁、并发和升级的用例需要独立的PostgreSQL测试库，并通过`POSTGRES_TEST_URL`指定。不要把它指向保存真实数据的数据库；测试会创建、修改或清理测试数据。

在可以清理的独立本地数据库上，一并运行数据库、后端、Flutter和部分教务解析检查，可以使用：

```powershell
.\scripts\dev.ps1 -Action Test
```

这个脚本会把`.env`中的`DATABASE_URL`作为PostgreSQL测试地址，因此应先确认它指向测试库。已有日常数据的开发库不适合直接使用这条命令，可另外设置独立的`POSTGRES_TEST_URL`并手动运行pytest。

脚本的JavaScript步骤只列了河南工大的reader测试。需要完整检查当前教务脚本时，再分别运行：

```powershell
node --test apps/mobile/test/haut_reader_test.cjs
node --test apps/mobile/test/hlju_reader_test.cjs
node --test apps/mobile/test/hlju_browser_compat_test.cjs
```

Flutter测试与静态分析在移动端目录运行：

```powershell
Set-Location apps/mobile
flutter pub get
flutter analyze
flutter test
```

结果有失败或跳过时，记录原因和影响的功能。一次测试结果只对应当时的代码和环境，文档里的旧数量不能代替重新执行。

## 2. 修改不同功能时，重点检查什么

| 修改内容 | 至少应检查的情况 |
| --- | --- |
| 通知整理 | 一条通知包含多个事项、只有开始时间、没有截止日期、补充和更正 |
| 活动冲突 | 开始落在课程内、恰好在课程结束时开始、只请某一次课、明确保留重叠 |
| 任务安排 | 缺少估时、等待审批、普通未填起点、需要一次完成、允许分段、容量不足 |
| 重新安排 | 固定块不动、未选任务不动、总工作量不变、不会删掉新活动 |
| 保存和撤销 | 先核对后保存、重复点击、另一个操作已修改数据、撤销会造成新冲突 |
| 页面和动画 | 连续切换、动画中再次点击、长文字、大字号、减少动画模式 |
| 账号和导入 | 切换账号不串数据、重复导入、学期选错、教务页面变化 |
| 提醒 | 权限关闭、修改时间、取消事项、重启、退出账号和点击通知 |

相应测试分布在`services/api/tests`和`apps/mobile/test`，文件名一般按功能命名。修改一个功能时，先运行对应测试，再根据影响范围决定是否运行整套测试。

## 3. 在模拟器上走完整流程

使用单独的QA包和临时数据库，避免改动日常使用的数据。QA包名为`cn.semesteros.semester_os.qa`，构建时通过`-PsemesterosQa=true`启用。后端入口是`scripts/app_flow_qa_server.py`，它只监听本机并使用临时SQLite，同时运行真实助手处理线程。

项目提供`scripts/test-app-flows.ps1`，包含`records`、`controls`和`management`三个流程。运行前先启动隔离后端，并确认模拟器就绪。该脚本使用本机SDK路径和指定的Android构建工具版本，换电脑时需要检查这些工具是否齐全。

人工或自动化操作时，至少保留输入内容、保存前后的数据、关键截图和失败提示。截图显示“等待处理”，就只能说明当时还在处理，不能拿它证明方案已经展示完成。

本轮操作的具体步骤和结果见[模拟器验证报告](参赛资料/拾日模拟器验证与算法测试报告.md)。

## 4. 现在已有的验证

2026年10月9—10日的隔离测试包括8组后台流程、3组任务前提与拒绝测试、9组模拟器主线、3个重排目标对照场景，以及一对手工表单与AI录入对照。另有一次独立的首次方案预览和拒绝操作。

这些测试使用合成课程、任务和新账号，部分调用真实文字模型。它们能说明所列场景的实际处理结果，不能换算成总体识别准确率或学生节省时间的比例。详细输入和机器结果保存在[原始测试目录](参赛资料/验证证据/aic-20261009/README.md)。

物理手机提醒到达、不同厂商省电策略、真实教务账号登录、多样本用户试用和Release性能没有被这轮模拟器测试覆盖。

## 5. 参赛材料怎么准备

目前已有作品方案、软件设计资料、核心算法说明、演示脚本和测试报告。还需要实际录制演示视频、制作答辩材料、补齐团队信息，并按比赛要求整理最终提交文件。

作品方案要先说明学生遇到什么问题，再说明拾日怎么处理，随后介绍实现和实际验证。模型、求解器和识别组件应写明使用了哪些第三方技术；项目自己的工作是如何组织课程、通知、任务和确认流程，不能把第三方能力写成自主研发成果。

演示数据使用虚构课程、地点和任务，不展示真实教务凭据、聊天联系人或学生信息。团队编号、试用人数、获奖、软著和其他成果，只填写已经取得的内容。

用户提供的比赛规则中，作品名称不超过20字，简介不超过300字；作品方案为PDF且不超过10MB；演示视频为MP4，时长3—5分钟、大小300MB以内；答辩材料也提交PDF。最终以[原始规则](2026AIC算法创新赛赛题规则汇总260506-1.pdf)及报名系统要求为准。

## 6. 不要把演示和实验混在一起

演示视频可以压缩等待，但不能据成片时长计算操作速度。手工录入与AI整理的比较必须采用相同输入、相同保存要求，并计入核对和改错时间。

目前一对自动化操作中记录了手工9个步骤、AI5个步骤。这只是该条输入的操作路径，不是一次真人效率实验。要报告实际使用收益，还需要更多输入、多位参与者和相对平衡的操作顺序。
