# 测试与参赛准备

测试要回答两个不同的问题：程序有没有按规则处理数据，用户能不能在真实界面上把事做完。后端测试全绿不代表界面能用，模拟器上顺也不代表每台手机都这样。

先说结论性的东西：这轮验证能证明列出来的那些场景当时是怎么处理的，证明不了总体识别准确率，也证明不了学生因此省了多少时间。这句话后面还会出现，因为参赛材料里最容易犯的错就是把这几个数混着说。

## 1. 日常怎么测

后端依赖装好之后，从仓库根目录：

```powershell
.\services\api\.venv\Scripts\python.exe -m pytest services/api/tests -q
```

大部分用例用临时 SQLite。涉及 PostgreSQL 行锁、并发、迁移的那部分要一个独立的 PostgreSQL 测试库，用 `POSTGRES_TEST_URL` 指过去。**别把它指到存着真实数据的库上**，测试会建、会改、也会清数据。

想一次把数据库、后端、Flutter 和部分教务解析都跑一遍：

```powershell
.\scripts\dev.ps1 -Action Test
```

这条命令会把 `.env` 里的 `DATABASE_URL` 当成 PostgreSQL 测试地址用，所以跑之前先确认那玩意儿指向的是测试库。平时在用的开发库别直接上这条，另设一个 `POSTGRES_TEST_URL`、手动敲 pytest 更稳。

脚本里的 JavaScript 那步只列了河南工大的 reader 测试。要把三个都查一遍，自己跑：

```powershell
node --test apps/mobile/test/haut_reader_test.cjs
node --test apps/mobile/test/hlju_reader_test.cjs
node --test apps/mobile/test/hlju_browser_compat_test.cjs
```

Flutter 那边：

```powershell
Set-Location apps/mobile
flutter pub get
flutter analyze
flutter test
```

有失败或者跳过，把原因和影响的功能记下来。一次结果只对应当时的代码和环境，文档里写过的旧数量不能当成本次跑过的证据。

## 2. 改哪块，重点看哪些情况

| 改了什么 | 至少要过一遍 |
| --- | --- |
| 通知整理 | 一条通知里多件事、只有开始时间、没有截止日期、补充和更正 |
| 活动冲突 | 开始落在课内、正好卡在课程结束那一刻、只请某一次课、明确要重叠 |
| 任务安排 | 缺估时、等审批、没填起点、要一次做完、允许分段、容量不够 |
| 重新安排 | 固定块不动、没选的任务不动、总工作量不变、不删掉后来的活动 |
| 保存和撤销 | 先核对再存、连点两下、别处已经改过数据、撤销会造成新冲突 |
| 页面和动画 | 连续切换、动画没完又点、长文字、大字号、减少动画 |
| 账号和导入 | 切账号不串数据、重复导入、学期选错、教务页面改版 |
| 提醒 | 权限关了、改时间、取消事项、重启、退出账号后点通知 |

对应测试在 `services/api/tests` 和 `apps/mobile/test`，文件名基本跟着功能走。改一个功能先跑相关的那几个，再按影响范围决定要不要全套。

## 3. 模拟器上走完整流程

用单独的 QA 包和临时数据库，别动日常在用的数据。QA 包名是 `cn.semesteros.semester_os.qa`，构建时加 `-PsemesterosQa=true`。后端用 `scripts/app_flow_qa_server.py`，它只监听本机、用临时 SQLite，并且会真的把助手的处理线程跑起来。

`scripts/test-app-flows.ps1` 里有 `records`、`controls`、`management` 三条流程。跑之前先把隔离后端起好、确认模拟器就绪。这脚本写死了本机的 SDK 路径和 Android 构建工具版本，换台电脑得先看这些工具齐不齐。

不管手工点还是自动跑，都留着输入内容、保存前后的数据、关键截图和失败提示。截图停在“等待处理”只说明当时还在处理，拿它证明“方案已经展示完整”是不成立的。

这一轮的输入、操作和结果在[原始验证记录](参赛资料/验证证据/aic-20261009/README.md)。

## 4. 现在已经验过什么

2026 年 10 月 9 日到 10 日那轮隔离测试包含：8 组后台流程、3 组任务前提与拒绝、9 组模拟器主线、3 个重排目标对照场景，外加一对手工表单和 AI 录入的对照。另外单独做过一次首次方案预览和拒绝。

这些用的是合成课程、合成任务和新账号，有一部分调了真实的文字模型。它们说明的是所列场景当时实际怎么处理，换不成“总体识别准确率”，也换不成“学生省了多少时间”。原始输入和机器结果在[原始测试目录](参赛资料/验证证据/aic-20261009/README.md)。

没覆盖到的：物理手机上的提醒到达、不同厂商的省电策略、真实教务账号登录、多样本用户试用、Release 包的性能。

1.1.1 这版补了标签词表、自动合并、来源保留、跨学期关联查询、翻页重试、账号切换保护的测试。移动端全量 593 项通过，静态分析没报问题；后端回归里关于发布版本的断言跟着 1.1.1 改过了。本版的结果记在[交付说明](交付说明.md)，PostgreSQL 专项和 SQLite 那部分是分开记的，别加在一起说。

历史实验保留它当时的版本和输入。新版本的回归不能拿去替换旧的算法测量，一次线上合成账号的验证也推不出总体准确率或者所有厂商真机的表现。

## 5. 参赛材料怎么弄

现在手上有的：作品方案、软件设计资料、核心算法说明、演示脚本、测试报告，以及一个已经成片的完整演示视频。提交前对一遍最终答辩材料、团队信息、文件格式和平台要求。加了新功能要补拍，就按实际装到机器上的那个版本重录。

作品方案的路子建议是：学生到底卡在哪儿 → 拾日怎么处理 → 怎么实现的 → 实际验到了什么。用到的模型、求解器、识别组件得写明是哪些第三方技术。项目自己干的那部分是“怎么把课程、通知、任务和确认流程串起来”，这个跟“自己训了个模型”是两回事，不能混着写成自主研发。

演示数据一律用虚构的课程、地点和任务，别露真实教务账号、聊天联系人、学生信息。团队编号、试用人数、获奖、软著这些，只写已经拿到手的。

赛题规则里这几条要记着：作品名称不超过 20 字，简介不超过 300 字；作品方案交 PDF，不超过 10MB；演示视频 MP4，3 到 5 分钟，300MB 以内；答辩材料也是 PDF。以[原始规则](2026AIC算法创新赛赛题规则汇总260506-1.pdf)和报名系统的要求为准。

## 6. 演示和实验别混着说

演示视频可以剪掉等待，但剪完之后不能拿成片时长去算操作速度。手工录入和 AI 整理的对比必须同样的输入、同样的保存要求，而且要把核对和改错的时间算进去。

现在有一对自动化操作记到手工 9 步、AI 5 步。这只是那一条输入的操作路径，不是真人效率实验。要说实际收益，得多几条输入、多几个人、把操作顺序也做个平衡。

## 7. 资料维护

Markdown、软件设计 Word 和视频脚本已经同步到 1.1.1。官方赛题 PDF 是原始材料，带日期的验证文件是历史证据，这两类不改。完整功能归档见[功能清单](功能清单.md)，接口索引是对着路由核出来的。

演示视频 2026-10-17 核对过：4 分 52 秒，54,386,609 字节，落在 3 到 5 分钟、300MB 以内这个范围里。早期脚本里写的“尚需录制”指的是原计划，现在那份脚本已经注明成片和需要补拍的部分。发布了新 App 不等于重做了视频，提交前画面、旁白、平台要求都还得再看一遍。
